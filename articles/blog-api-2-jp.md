前回の記事では、Go言語による Note & Qiita への同時投稿の基礎をお伝えしました。しかし、最後まで残った大きな壁――それが **「Note で Gist のテーブル（表）が表示されない問題」** でした。

数時間にわたるデバッグと Network タブとの対話の末、ついに「開発者が仕掛けた鍵」を見つけたので共有します。

> **【重要】**本記事は技術的な探求および検証の結果を記録したものであり、**非公式 API の利用を推奨するものではありません。**サーバーへの過度な負荷を避けるための適切なインターバルの設置や、規約を尊重した利用など、開発者としてのモラルを持った行動を前提としています。

---

## 1. 「空の箱」は門前払い：Note の徹底したバリデーション

当初、私はこう考えていました。「GitHub Gist でファイルを作って、その URL を入れた <figure> タグを送れば、あとは Note 側が勝手に展開してくれるだろう」と。

しかし、現実は甘くありませんでした。

- **現象**: プログラムから送った figure タグが、保存した瞬間にただの「リンク」に格下げされる。
- **原因**: Note のサーバーは、保存時に「既に展開済みの正しい構造」が含まれているかを厳格にチェックしていました。中身のない figure は、彼らにとって「不完全なデータ」だったのです。

## 2. YouTube は動くのに、なぜ Gist はダメなのか？

YouTube の埋め込みは URL を含めたシンプルな構造で（なぜか？）成功していました。しかし、Gist（やその他の外部サービス）は **Iframely** という仲介役を介して展開されます。

ここには開発者の巧妙なロジックがありました。YouTube は「特別扱い」で自前展開するけれど、サードパーティの埋め込みには **「Iframely が発行した正規の通行手形（ハッシュ ID）」** を要求していたのです。

## 3. 「公式の通行手形」を奪取する：逆転の発想

自前で Iframely の構造を偽造するのは困難でした。ならばどうするか？**「Note 自身が埋め込み用に生成した HTML を、そのまま流用させてもらう」** のが唯一の正解でした。

解析の結果、判明したフローがこちら：

check_type API で URL の正当性を確認。
embed_by_external_api を叩き、Note サーバーが生成した「公式 HTML（Iframely の ID 入り）」を取得。
その **「お墨付き」の HTML を自分のリクエストにハメ込んで PUT する。**

これにより、サーバー側のバリデータを「これは間違いなくうちのエディタが作ったデータだ」と完璧に誤認させることに成功しました。

---

## 4. 開発を通じて感じた「面白さ」

今回のハックを通じて、Note の開発チームがいかにセキュリティと表示の整合性を守ろうとしているかがよく分かりました。「仕様書がない」ということは、「開発者の思考をトレースする」という最高のパズルを楽しめるということでもあります。

無機質な API 連携が、一気に人間味のある知恵比べに変わった瞬間でした。
